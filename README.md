# 売上伝票の自動読み取り × 荷主ごとの料金ルール整理エンジン（sales-slip-ocr-automation）

**紙の伝票をカメラで読み取って自動入力するだけでは、荷主ごとにバラバラな料金体系の問題は解決しません。** 全国で1日約10,000件（架空）の伝票が処理され、大半の拠点で複数の荷主が同時に取引している規模を想定し、伝票の自動読み取りから料金確定までの流れを、合成データだけで再現したデモです。

> ⚠️ すべてのデータは合成（架空）データです。実在企業のコスト実績・荷主情報は一切含まれていません。詳細は [docs/design.md](docs/design.md) の「1. 匿名化・安全設計」を参照してください。

## 課題ストーリー

- 売上伝票は4種類あり、そのうち3種類（自社手書き・荷主指定様式・代理店伝票）が自動読み取りの対象です（荷主とシステム連携済みの電子伝票は対象外）
- 集荷した時点では、実際の重さや追加作業の有無、車を貸し切るかどうかがまだ決まっていないことが多く、後工程で内容を確定させて基幹システムに反映する必要があります
- 全国には多くの荷主（取引量の多い主要荷主に加え、少量ずつ取引する荷主も多数）が同時に取引しており、荷主ごとに異なる料金・作業条件を、現状は人手で管理しています
- 荷主の数が多い拠点ほど、この個別対応の手間が積み重なります。伝票の自動読み取りだけでは解決しない、本当の課題はここにあります
- 一方で、荷主ごとにきめ細かく対応できることは大手にはない自社の強みでもあり、単純になくすわけにもいきません
- **参考**: 一部の拠点は取引先が1社に固定されているため、外部の表計算とシステム連携だけの簡易な運用が例外的に成立しています。ただしこれは全国的には少数のケースです

この課題に対し、荷主ごとの料金・条件を一元管理する「ルールエンジン」という仕組みを提案し、取引先の数（1〜60社、全国規模を想定）が増えるほど運用の手間がどう変わるかをシミュレーションします。

### 画面

1. **課題サマリー** — 伝票の内訳と課題の要点
2. **読み取りシミュレーション** — 伝票の種類ごとに読み取り精度がどう変わるかを確認し、どこまで自動承認するかの基準をスライダーで調整
3. **料金確定の流れ** — 読み取り結果から重量確定・輸送方法・追加作業判定・基幹システム登録までの各ステップと自動化の度合いを可視化
4. **荷主ごとの料金ルール一覧・運用工数比較** — 荷主数を増やしたとき、ルールを一元管理する仕組みの有無で運用の手間がどれだけ変わるかを比較
5. **効果試算** — 荷主数に応じた月間の作業工数をダミー数値で試算
6. **打ち手の比較（経営判断）** — 入力の自動化・システム改修・特別対応の標準化といった複数の打ち手を、投資回収期間で比較。答えを1つに絞らず、複数の選択肢として提示

すべての数値は、再現できるダミー乱数から生成した合成データです。

## 設計思想

- **打ち手を1つに決め打ちしない**：自動読み取りとルールエンジンは有力な案の1つに過ぎず、システム改修や料金体系の見直しなど、原因の異なる複数の打ち手を並べて比較しています
- 実際の読み取りエンジンそのものの実装は対象外とし、読み取ったあとの業務の流れと経営判断の設計に焦点を当てています
- 実際の取引先情報やコスト実績は一切使用せず、架空の前提値だけで組み立てています
