# 売上伝票の自動読み取り × 荷主ごとの料金ルール整理エンジン（sales-slip-ocr-automation）

**紙の伝票をカメラで読み取って自動入力するだけでは、荷主ごとにバラバラな料金体系の問題は解決しません。** 全国で1日約10,000件(架空)の伝票が処理され、大半の拠点で複数の荷主が同時に取引している規模を想定し、伝票の自動読み取りから料金確定までの流れを合成データだけで再現したデモです。

> ⚠️ すべてのデータは合成(架空)データです。実在企業のコスト実績・荷主情報は一切含まれていません。詳細は[docs/design.md](docs/design.md)の「1. 匿名化・安全設計」を参照してください。

## 背景と解決したい課題（Why）

売上伝票は4種類あり、そのうち3種類(自社手書き・荷主指定様式・代理店伝票)が自動読み取りの対象です。集荷した時点では実際の重さや追加作業の有無、車を貸し切るかどうかがまだ決まっていないことが多く、後工程で内容を確定させて基幹システムに反映する必要があります。全国には多くの荷主(取引量の多い主要荷主に加え、少量ずつ取引する荷主も多数)が同時に取引しており、荷主ごとに異なる料金・作業条件を、現状は人手で管理しています。荷主の数が多い拠点ほど、この個別対応の手間が積み重なります——**伝票の自動読み取りだけでは解決しない、本当の課題はここにあります。**

最初の設計では、この課題を「特定荷主に依存した商流の問題」として捉えていましたが、掘り下げる過程で、荷主と合意した包括運賃は実は既に適用済みであり、真因は商流ではなく**基幹システムにその運賃体系が反映されていないこと**にあると再整理しました。この診断の訂正自体が、課題設定を一段深めるプロセスの記録になっています。

## 誰のためのツールか、どう自分たちに応用するか

**対象読者**: 複数荷主・複数料金体系を抱える3PL拠点の売上処理・料金確定業務担当者、または基幹システム刷新を検討する情シス担当。

**応用方法**: 二層レート(Layer1基本包括/Layer2特別適用)は荷主コードと適用条件をキーにした構造に分離してあるため、自社の実際の運賃契約(基本料金表+特約条件)をこの2層にマッピングし直すだけで、運用工数比較シミュレーターに自社の荷主構成を反映できます。荷主数が少ない(1社に固定されている)拠点では、この仕組みは過剰設計になり得る点も[docs/design.md](docs/design.md)に明記しています——導入前に「自社は何社の荷主と同時に取引しているか」を確認することが最初のステップです。

## 機能概要とアーキテクチャ（What / How）

単一`index.html`(Tailwind CDN + Vanilla JS + SVG、`mulberry32`シード付き疑似乱数)。ビルド不要でブラウザで開くだけで動作します。

1. **課題サマリー** — 伝票の内訳と課題の要点
2. **読み取りシミュレーション** — 伝票の種類ごとに読み取り精度がどう変わるかを確認し、どこまで自動承認するかの基準をスライダーで調整
3. **料金確定の流れ** — 読み取り結果から重量確定・輸送方法・追加作業判定・基幹システム登録までの各ステップと自動化の度合いをSVGフロー図で可視化
4. **荷主ごとの料金ルール一覧・運用工数比較** — 二層レート(基本包括Layer1 + 特別適用Layer2)で、荷主数を増やしたときにルールを一元管理する仕組みの有無で運用の手間がどれだけ変わるかを比較
5. **効果試算** — 荷主数に応じた月間の作業工数をダミー数値で試算
6. **打ち手の比較(経営判断)** — 入力の自動化・システム改修・特別対応の標準化といった複数の打ち手を、投資回収期間・36ヶ月NPVで比較。答えを1つに絞らず、複数の選択肢として提示

デモ: https://logtk.github.io/sales-slip-ocr-automation/ (`main`へpushすれば数分後に自動反映)

## 現在のステータスと直面している課題（Current Status & Technical Challenges）

課題サマリーから経営オプション比較まで、6画面すべてが動作する状態まで実装が完了しています。設計上、意図的にスコープを絞っている点と、実装過程で見えた構造的な課題を明記します。

**意図的なスコープ外: OCRエンジン自体の実装**

実際の文字認識エンジンの実装はこのデモの対象外です。これは技術的に難しいから避けたのではなく、掘り下げの結果「本当の課題はOCR精度ではなく、読み取った後の料金ルール管理の構造にある」と診断したためです。読み取り後の業務フローと経営判断の設計にリソースを集中させる、という意図的なスコープ設定です。

**構造的課題: 二層レートモデルの粒度**

現在のLayer1(基本包括マスター)/Layer2(特別適用オーバーライド)という二層構造は、荷主単位でのルール管理を前提にしています。実際の伝票を接続する段階では、同一荷主内でも配送先・商品カテゴリ単位で例外条件が発生するケースがあると想定しており、Layer2のキー設計(荷主単位か、荷主×条件の複合キーか)は実データを見てから精緻化が必要な仮説段階の設計です。

## 今後の展望（Next Steps）

- 二層レートモデルを、実際のOCR抽出結果(重量・輸送方法・追加作業フラグ)と接続するプロトタイプへの発展。
- 経営オプション比較(A〜E)の感度分析パラメータを、実際の伝票内訳データが取得できた場合にキャリブレーションする仕組み。
- **生成AIによる特別適用条件の自然言語抽出**: 現状は手動登録前提のルールエンジンですが、伝票の備考欄や過去のメールのやり取りといった自由記述から、Layer2に登録すべきルール候補をLLMで抽出できれば、二層レートモデルの運用工数をさらに削減できると考えています。ここは強いエンジニアリングとの協業で検証したい領域です。

## 設計思想

- **打ち手を1つに決め打ちしない**: 自動読み取りとルールエンジンは有力な案の1つに過ぎず、システム改修や料金体系の見直しなど、原因の異なる複数の打ち手を並べて比較しています
- 実際の取引先情報やコスト実績は一切使用せず、架空の前提値だけで組み立てています
